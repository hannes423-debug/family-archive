# Family Archive

A long-term digital family archive — not just a genealogy chart, but the place
photographs, documents, stories and relationships are meant to survive in.

**The published tree: https://hannes423-debug.github.io/family-archive/**

---

## ⚠️ This repository is public. The family data is not.

Read this before committing anything.

The source genealogy contains living people, including children — full names,
exact dates of birth, birth places. **None of it is in this repository**, and it
must stay that way. It lives offline in `data/`, which `.gitignore` excludes
wholesale.

What ships instead is `docs/data/tree.json`, generated by `tools/build_site.py`,
in which every living person is reduced to a surname. The rules and the reasoning
are on the [privacy page](https://hannes423-debug.github.io/family-archive/privacy.html),
which the site itself links to.

Three things enforce this, deliberately independent of one another:

| Guard | Where | What it stops |
|---|---|---|
| `.gitignore` | `/data/`, `*.ged`, `tree.private.json` | The source data being staged at all |
| `build_site.py` | whitelist redaction + a self-check | The generator emitting a living person's fields |
| `verify_public.py` | pre-push hook, and CI once the workflow is installed | Anything that got past the first two reaching the web |

If you ever need the full tree locally, build it and keep it local:

```bash
python3 tools/build_site.py --include-living   # -> docs/data/tree.private.json
```

That path is gitignored. Open the site with `?private=1` to view it; the header
turns into a warning so an unredacted build cannot be mistaken for the public one.

## The published site

`docs/` is plain HTML, CSS and one JavaScript file. No build step, no
dependencies, no framework — what is in the repo is byte-for-byte what deploys.
It is called `docs/` because that is the folder GitHub Pages can serve straight
from a branch (see [Deployment](#deployment)).

```bash
python3 -m http.server 8000        # from the repo root
# then open http://localhost:8000/docs/
```

The tree is laid out as a small Sugiyama: people are grouped into units (a couple
or a single person), placed in layers by generation, ordered within each layer by
barycentre sweeps, then positioned by a priority pass that pulls each unit toward
its relatives and pushes overlaps apart. That is what lets two separate ancestral
lines merge lower down when their descendants marry — which is most of this tree,
and the case a plain recursive layout cannot draw.

### Regenerating the data

```bash
python3 tools/build_site.py        # curated GEDCOM -> docs/data/tree.json
python3 tools/verify_public.py     # prove the result is safe to publish
```

### Testing

`tools/drivertest.html` drives the real page in an iframe — real events on real
elements — and asserts both that the UI works and that no living person's data
reaches the rendered output.

```bash
python3 -m http.server 8123 &
google-chrome --headless=new --disable-gpu --virtual-time-budget=20000 \
  --dump-dom http://127.0.0.1:8123/tools/drivertest.html | grep -o '<title>[^<]*'
# -> DONE 25/25
```

## Deployment

GitHub Pages serves `docs/` on the `main` branch directly — **Settings → Pages →
Source: Deploy from a branch → `main` / `docs`**. Every push to `main` publishes.

Run the guard yourself before pushing, because a branch deploy has no CI gate:

```bash
python3 tools/verify_public.py     # exits non-zero if anything would leak
```

Better, install it as a hook so it cannot be forgotten:

```bash
printf '#!/bin/sh\nexec python3 tools/verify_public.py\n' > .git/hooks/pre-push
chmod +x .git/hooks/pre-push
```

### Moving to the Actions workflow

`tools/github-pages-workflow.yml` is a ready-made Actions deploy that runs
`verify_public.py` as a hard gate before publishing — strictly better than the
branch deploy, because the check runs on the server rather than on trust.

It is parked in `tools/` rather than installed because pushing a file under
`.github/workflows/` needs a token with the `workflow` scope, and the one on
this machine only has `repo`. Once your token has `workflow`:

```bash
mkdir -p .github/workflows
git mv tools/github-pages-workflow.yml .github/workflows/pages.yml
git commit -m "Deploy Pages via Actions, with the leak check as a gate"
git push
```

Then switch **Settings → Pages → Source** to **GitHub Actions**.

## Repository layout

```
design/ARCHITECTURE.md  The full platform design — data model, sync, media,
                        auth, risks, and a 13-phase roadmap. Written before any
                        code, on purpose.
docs/                   The published tree. Served by GitHub Pages as-is.
tools/                  Redaction, verification, browser test, parked workflow.
data/                   Private source genealogy, plus the curation scripts that
                        contain living people's names. GITIGNORED — never
                        committed, not present in any commit in this history.
```

## Where this is going

`design/ARCHITECTURE.md` describes the real target: assertion-based storage, where
every fact is a claim with a confidence level, a status and citations, and a
person record is a cached projection over those claims. Verification, sources,
non-destructive import, revert and a year-by-year time machine all fall out of
that structurally instead of being bolted on afterwards.

The site in this repository is the first visible piece of it, not the whole plan.
Phase 3 of the roadmap replaces `tools/build_site.py` with a real importer that
lands the GEDCOM on a UI-validated data model.
